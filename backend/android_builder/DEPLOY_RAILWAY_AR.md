# نشر عامل بناء Android على Railway (خدمة خاصة)

هذا الدليل يجهّز خدمة بناء APK مستقلة عن API. لا تنشرها كخدمة عامة ولا تضع سرها في Git أو ZIP. إنشاء الخدمة وتشغيلها قد يستهلك موارد مدفوعة؛ لا تنفذ ذلك إلا بعد اختيار المستخدم للخطة/المشروع والموافقة على التكلفة.

## إعداد الخدمة

1. أضف خدمة جديدة داخل مشروع Railway نفسه الذي يستضيف NatqAI API، واختر مستودع NatqAI نفسه والفرع الذي يحتوي هذه الملفات.
2. اضبط **Root Directory** على `/backend`.
3. اضبط **Config File** على `/android_builder/railway.json` (إذا كانت واجهة Railway تطلب مساراً نسبياً إلى جذر المستودع فاستخدم `backend/android_builder/railway.json` بدلاً منه).
4. تأكد أن إعداد البناء يستخدم Dockerfile `android_builder/Dockerfile`.
5. أنشئ متغيراً سرياً `ANDROID_BUILDER_TOKEN` بقيمة عشوائية قوية لا تقل عن 32 بايت. لا تستخدم قيمة المثال ولا تحفظ السر في المستودع.
6. فعّل الشبكة الخاصة للخدمة واجعل اسم نقطة الاتصال الخاصة `natqai-android-builder` إن كانت هذه الخاصية متاحة في إعدادات الخدمة.
7. لا تضف Public Domain أو TCP Proxy للعامل. يجب أن يكون متاحاً من API عبر الشبكة الخاصة فقط.
8. بعد نجاح النشر، يستخدم Railway المسار العام `/health` لفحص حياة خدمة HTTP فقط؛ هذا المسار لا يحتاج رمزاً سرياً. بعد ذلك يتحقق NatqAI API من `/ready` عبر الشبكة الخاصة مع ترويسة `Authorization: Bearer ...`، وهذا الفحص وحده يؤكد وجود Gradle وJDK وAndroid SDK وapksigner. لا تضبط فحص Railway على `/ready` لأنه محمي بالمصادقة ولن يرسل Railway الرمز السري.

## ربط API

في خدمة NatqAI API نفسها، أضف المتغيرين التاليين في البيئة نفسها:

- `ANDROID_BUILDER_URL=http://natqai-android-builder.railway.internal:8080`
- `ANDROID_BUILDER_TOKEN` = **نفس السر** الذي وضعته في خدمة العامل.

لا ترسل السر إلى واجهة المتصفح ولا تضعه في ملفات المشروع. أعد نشر API بعد ضبط المتغيرات. ثم افتح مساحة مشروع في NatqAI واضغط «بناء APK وتنزيله». يفحص التطبيق حالة العامل أولاً ثم يبدأ البناء فقط عند الجاهزية.

## تحقق قبل اعتبار التكامل مكتملاً

- حالة نشر عامل البناء في Railway هي `SUCCESS`.
- فحص Railway `/health` ينجح، ثم فحص `/ready` المصادق عليه ينجح من داخل شبكة API الخاصة.
- حالة `android-builder-status` في NatqAI تعرض `ready`.
- بناء مشروع تجريبي يعيد ملف APK، ويتحقق API من ZIP ووجود `AndroidManifest.xml` و`classes.dex`.
- جرّب تثبيت APK على جهاز Android فعلي. هذا البناء Debug للتجربة وليس إصداراً موقعاً للنشر على Google Play.

## حدود الأمان والتشغيل

- أبق العامل خاصاً، ولا تضعه خلف نطاق عام.
- لا تشارك `ANDROID_BUILDER_TOKEN` ولا تطبعه في السجلات.
- راقب الذاكرة والوقت والتكلفة؛ Gradle/SDK يحتاجان موارد ملموسة.
- حدّث السر في الخدمتين معاً عند تدويره.
- لا تعتبر فحص ZIP وحده دليلاً على أن التطبيق يعمل على جهاز Android.

## تحقق أمني إضافي في API

يرفض API عنوان عامل البناء إذا كان HTTP عاماً، أو احتوى بيانات اعتماد داخل URL أو مساراً أو query string. استخدم HTTPS، أو عنوان HTTP داخلياً ينتهي بـ `.railway.internal`، أو عنوان IP خاصاً موثوقاً في شبكة خاصة. لا تضع أي رمز سري داخل الرابط؛ المصادقة تتم حصراً عبر `ANDROID_BUILDER_TOKEN` في ترويسة Authorization.


**ملاحظة تحقق التوقيع (v32):** يجب أن تتضمن صورة العامل أداة `apksigner` ضمن Android SDK Build Tools 35. يفحص العامل توقيع APK قبل إرساله؛ ونجاح فحص توقيع Debug لا يعني أن التطبيق موقّع بمفتاح إصدار إنتاجي.
